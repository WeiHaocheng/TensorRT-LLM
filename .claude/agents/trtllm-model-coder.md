# TensorRT-LLM Modeling Coder Skill

This skill provides guidance for implementing TensorRT-LLM modeling code based on a porting plan (`plan.md`) produced by the `trtllm-model-analysis` skill. The final output is a fully functional `modeling_*.py` file placed under `tensorrt_llm/_torch/models/`.

## Overview

The Modeling Coder skill takes a porting plan and produces:

1. **Modeling File** (`modeling_<model_name>.py`): A complete Python module containing:
   - Attention class (inheriting from `Attention` or `QKNormRoPEAttention`)
   - DecoderLayer class (inheriting from `DecoderLayer`)
   - Model class (inheriting from `DecoderModel`)
   - ForCausalLM class (inheriting from `DecoderModelForCausalLM`)
   - Model registration via `@register_auto_model`
   - Custom weight loading logic (if needed)

2. **Registration**: The model is registered with `@register_auto_model` and added to `__init__.py`.

### ⚠️ Output Constraints

1. **Output only the modeling file and necessary registration changes.** Do NOT generate test code, documentation, or configuration files unless explicitly requested.
2. **Follow existing TRT-LLM patterns exactly.** Use the same coding style, import conventions, and class hierarchies as existing models (e.g., `modeling_llama.py`, `modeling_qwen.py`).
3. **All parameters use keyword-only arguments** (`*` in the signature) for TRT-LLM module constructors.

## Inputs

| Input | Description | Example |
|-------|-------------|---------|
| `plan_path` | Path to the porting plan generated by the analysis skill | `./plan.md` |
| `modeling_path` | (Optional) Path to an existing TRT-LLM modeling file to modify | `tensorrt_llm/_torch/models/modeling_llama.py` |
| `modify_feedback` | (Optional) Key modifications to focus on in this agent run. Use this to direct the coder's attention to specific areas that need changes. | `Weight loading: split concatenated HF QKV weight along dim=0 to match separate Q/K/V projections.` |

### ⚠️ CRITICAL: `plan.md` is the Single Source of Truth

**All code development MUST strictly follow the content of `plan.md`.** The porting plan is the authoritative specification for:
- Module selection and class hierarchy
- Constructor parameter mappings
- Weight name mappings and format conversions
- Architecture decisions and special handling requirements

**Do NOT deviate from `plan.md` based on assumptions, external references, or personal judgment.** If any part of the plan appears incorrect or incomplete, stop coding and notify the user rather than silently working around it.

## Outputs

### Output 1: Modeling File

If `modeling_path` is provided, modify the existing file at that path. Otherwise, create a new Python file at `tensorrt_llm/_torch/models/modeling_<model_name>.py`.

### Output 2: Registration Updates

Updates to `tensorrt_llm/_torch/models/__init__.py` to import and export the new model class.

### Output 3: Module Usage Summary (only when `modeling_path` is NOT provided)

When generating a new modeling file from scratch (i.e., `modeling_path` is not provided), output a summary listing all TRT-LLM modules used in the generated code. **Skip this output when modifying an existing modeling file.** For each module, include:
- **Module class name**: The full class name (e.g., `Attention`, `GatedMLP`, `RmsNorm`, `Embedding`, `Linear`).
- **Import path**: The import path of the module (e.g., `tensorrt_llm._torch.modules.attention`).
- **Usage location**: Which model class uses this module (e.g., `GPTDecoderLayer.__init__`).
- **Constructor arguments**: The key arguments passed when instantiating this module.

## Workflow

> **Shortcut**: If the input includes `modeling_path`, the modeling file already exists—**skip Step 1 and go directly to Step 2** to verify and modify the existing file according to `plan.md` and `modify_feedback`.

### Step 1: Generate Modeling Code from plan.md

Read `plan.md` thoroughly, then generate the complete `modeling_<model_name>.py` file following the plan's specifications:

1. Read and internalize the full porting plan, including architecture overview, module mappings, weight mappings, and format conversion requirements. **`plan.md` is the single source of truth—all implementation decisions must be derived from it.**
2. If `modify_feedback` is provided, focus on the specified modifications during code generation.
3. Implement each class in order: Attention → DecoderLayer → Model → ForCausalLM.
4. For each class, select the correct TRT-LLM base class and modules as specified in `plan.md`.
5. Implement the `load_weights` method with all weight format conversions specified in the plan.

### Step 2: Verify Module Initialization Parameters Against plan.md

After generating the modeling code, perform a systematic verification of every module's initialization parameters:

1. For each module instantiated in the generated code, locate its corresponding entry in `plan.md`.
2. Compare every constructor argument in the generated code against the plan's parameter mapping table. Check:
   - **Parameter names**: Ensure the argument names match the TRT-LLM module's constructor signature exactly.
   - **Parameter values/sources**: Ensure each argument's value is correctly derived from the HuggingFace config field specified in the plan (e.g., `config.hidden_size`, `config.num_attention_heads`).
   - **Parameter completeness**: Ensure no required parameters are missing and no extraneous parameters are added.
   - **Default values**: Verify that parameters relying on default values are intentionally omitted and that the defaults are correct for this model.

### Step 3: Verify Weight Name Conversions Against plan.md

After verifying module parameters, perform a systematic verification of weight name mappings and format conversions:

1. For each weight mapping entry in `plan.md`, verify that the `load_weights` method correctly handles:
   - **Name mapping**: The HuggingFace weight name (e.g., `model.layers.{}.self_attn.q_proj.weight`) is correctly mapped to the TRT-LLM parameter name (e.g., `transformer.layers.{}.attention.qkv.weight`).
   - **Format conversion**: Any required transformations are applied (e.g., QKV concatenation, transposition, reshaping, dtype casting).
   - **Completeness**: All weights listed in the plan are handled—no weights are missing from `load_weights`.
2. Cross-check that the weight names used in `load_weights` are consistent with the module hierarchy defined in the generated model classes. For example, if the Attention class stores Q/K/V as a fused `qkv` linear layer, the weight loading must concatenate the separate HuggingFace Q/K/V weights accordingly.

## Fused Residual + Norm Pattern

For performance, decoder layers should use the fused residual+norm pattern where `RMSNorm(hidden_states, residual)` returns `(normed, new_residual)`:

```python
class MyDecoderLayer(DecoderLayer):
    def forward(self, ..., hidden_states, residual=None, ...):
        if residual is None:
            residual = hidden_states
            hidden_states = self.input_layernorm(hidden_states)
        else:
            hidden_states, residual = self.input_layernorm(hidden_states, residual)

        hidden_states = self.self_attn(hidden_states=hidden_states, ...)
        hidden_states, residual = self.post_attention_layernorm(hidden_states, residual)
        hidden_states = self.mlp(hidden_states, ...)
        return hidden_states, residual  # tuple!
```

The model's `forward` must handle the tuple and finalize with `self.norm(hidden_states, residual)`:

```python
class MyModel(DecoderModel):
    def forward(self, ...):
        hidden_states = self.embed_tokens(input_ids)
        residual = None
        for layer in self.layers:
            hidden_states, residual = layer(..., hidden_states=hidden_states, residual=residual)
        hidden_states, _ = self.norm(hidden_states, residual)
        return hidden_states
```

## aux_stream for MoE Chunking Overlap

MoE models should create an `aux_stream` in the Model class and thread it through to `create_moe`:

```python
class MyModel(DecoderModel):
    def __init__(self, model_config):
        super().__init__(model_config)
        self.aux_stream = torch.cuda.Stream()
        self.layers = nn.ModuleList([
            MyDecoderLayer(model_config, layer_idx, self.aux_stream) ...
        ])
```

Pass to `create_moe` via `aux_stream_dict={AuxStreamType.MoeChunkingOverlap: aux_stream}`.

## Custom MoE Gate with Bias

When the router has a bias term (uncommon but possible), implement a custom Gate class following the `Qwen3Gate`/`DeepseekV3Gate` pattern:

```python
class MyGate(nn.Module):
    def __init__(self, hidden_size, num_experts, top_k, dtype, moe_backend_cls):
        super().__init__()
        self.weight = nn.Parameter(torch.empty((num_experts, hidden_size), dtype=dtype))
        self.bias = nn.Parameter(torch.empty(num_experts, dtype=dtype))
        # ...

    def forward(self, hidden_states):
        return torch.ops.trtllm.cublas_mm(hidden_states, self.weight.t(),
                                           bias=self.bias, out_dtype=self.out_dtype)

    def load_weights(self, weights, allow_partial_loading=False):
        # Custom loading for weight + bias
        ...

    @property
    def routing_method(self) -> BaseMoeRoutingMethod:
        # Return appropriate routing method
        ...
```

The `routing_method` property must return the correct type (e.g., `RenormalizeMoeRoutingMethod` for top-k-then-softmax). Adjust `output_dtype` based on the MoE backend: `torch.bfloat16` for `TRTLLMGenFusedMoE`, `torch.float32` otherwise.

## Attention Sinks (Per-Head Learned Parameter)

Some models have per-head attention sink logits. Store as an `nn.Parameter` in the custom Attention class and pass via `attention_sinks` arg:

```python
class MyAttention(Attention):
    def __init__(self, model_config, layer_idx):
        super().__init__(...)
        # self.num_heads is already divided by tp_size
        self.sinks = nn.Parameter(torch.empty(self.num_heads, dtype=config.torch_dtype))

    def forward(self, ...):
        return super().forward(..., attention_sinks=self.sinks)
```

TP-slice sinks in `_transform_weights`: `value[tp_rank * heads_per_tp : (tp_rank+1) * heads_per_tp]`.

## Per-Layer Sliding Window Attention

For models with alternating sliding/full attention layers, control per-layer via `attention_mask` and `attention_window_size`:

```python
class MyAttention(Attention):
    def __init__(self, model_config, layer_idx):
        config = model_config.pretrained_config
        layer_type = config.layer_types[layer_idx]
        self.is_sliding = layer_type == "sliding_attention"
        self._window_size = config.sliding_window if self.is_sliding else None
        super().__init__(...)

    def forward(self, ..., attention_mask=None, **kwargs):
        if attention_mask is None:
            attention_mask = (PredefinedAttentionMask.SLIDING_WINDOW_CAUSAL
                              if self.is_sliding else PredefinedAttentionMask.CAUSAL)
        return super().forward(..., attention_mask=attention_mask,
                               attention_window_size=self._window_size, **kwargs)
```

## RoPE Configuration from Nested Config

Some HF configs store `rope_theta` inside a nested dict (`rope_parameters` or `rope_scaling`) rather than as a top-level attribute. `RopeParams.from_config(config)` handles this automatically — it calls `config.update(hf_rope_parameters)` which promotes nested keys to top-level attributes. Always use `RopeParams.from_config(config)` rather than manually extracting rope parameters.

## Router Key Renaming

HuggingFace often names the MoE router as `mlp.router`, while TRT-LLM expects `mlp.gate`. Handle in `_transform_weights`:

```python
if '.mlp.router.' in key:
    new_key = key.replace('.mlp.router.', '.mlp.gate.')
    transformed[new_key] = value
```

## ⚠️ Important Notes

1. **Strictly follow `plan.md` at all times**: Every implementation decision—module selection, parameter mapping, weight conversion, class hierarchy—**MUST** be derived from `plan.md`. Do not introduce any logic, parameter, or mapping that is not specified in the plan. If the plan does not cover a particular aspect, stop coding and notify the user rather than improvising.

2. **Select the correct modules from plan.md and verify initialization parameters**: Strictly follow the TRT-LLM modules specified in `plan.md` (e.g., `Attention`, `MLP`, `Linear`, etc.) when building the code. For each module class, carefully verify that the initialization parameters match the mappings in the plan, ensuring parameter names, types, and default values are correct.

3. **Override `load_weights` to implement weight format conversion**: Override the `load_weights` method in the ForCausalLM class. Implement custom weight loading logic according to the weight mappings and format conversion requirements specified in `plan.md` (e.g., QKV concatenation/splitting, transposition, dtype conversion, etc.).

4. **Evaluate whether base class interfaces are reusable**: Check whether the default interface implementations provided by the inherited base classes (e.g., `DecoderModelForCausalLM`) such as `forward`, `prepare_inputs`, etc., meet the current model's requirements. If the model has special forward logic or input handling, override the corresponding methods in the subclass.
   1. If the model's parameter name mapping or quantization exclusion module logic differs from the base class, override `__post_init__`.

5. **Check whether the module's backend is the default backend**: Verify whether each module selected in `plan.md` depends on a non-default backend (e.g., specific kernel implementations or custom ops). If non-default backend dependencies exist, **you must stop coding and notify the user**, letting the user decide how to proceed.

6. **Do not consider parallelism strategies**: You do not need to consider tensor parallelism (TP), data parallelism (DP), pipeline parallelism (PP), or any other distributed partitioning strategies. Focus solely on the single-GPU modeling implementation.
